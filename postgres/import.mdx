## Import data from another postgres cluster into your Managed Postgres Cluster

If you're migrating to Fly Managed Postgres (MPG) from an unmanaged Fly Postgres cluster or another Postgres provider, you'll need to import your data into your MPG cluster.

There isn't currently an automated way to migrate an existing DB's data, but you can accomplish this with a standard Postgres dump and restore process after creating your MPG cluster.

Your MPG cluster runs within your Fly.io private network, so it isn't reachable over the public internet. `fly mpg connect` opens the tunnel, looks up the credentials, and runs psql for you, so you can restore from your local machine without setting up a proxy or copying a password. You'll need `pg_dump` and psql installed locally, and flyctl v0.5.9 or later.

1. Create your Managed Postgres cluster from the Fly.io dashboard, or using `fly mpg create`

    <Warning>
    **Warning:** Your new cluster must be created with a volume at least as large as the database you're importing, otherwise the import process will fail.
    </Warning> 

2. Dump your existing database to a file
    ```bash
    pg_dump --no-owner --no-acl -f dump.sql "$LEGACY_PG_CONNECTION_STRING"
    ```

3. If your `pg_dump` is version 17 or later and your cluster runs Postgres 16, remove one setting from the top of the dump. `pg_dump` 17 and later writes `SET transaction_timeout = 0;` there, and Postgres 16 doesn't know that setting. Check your version with `pg_dump --version`
    ```bash
    sed '1,20{/^SET transaction_timeout = 0;$/d;}' dump.sql > dump-pg16.sql
    ```

    The `1,20` keeps the edit inside the dump's header, so it can't touch your data. Use `dump-pg16.sql` in the next step.

4. Restore the file into your MPG cluster. Find the cluster ID with `fly mpg list`
    ```bash
    fly mpg connect <CLUSTER_ID> -f dump.sql -- -q --single-transaction
    ```

    `-q` keeps psql quiet, so errors stand out. `--single-transaction` makes the restore all-or-nothing: if it stops for any reason, nothing is left behind and you can run it again. The restore goes into the default database as the default user. Add `--database` or `--username` to pick others.

5. Check the result. A restore that worked prints no errors and exits with status `0`. One that failed prints psql's error and a line like `Error: exit status 3`, and exits with status `1`.

### Restore errors

- **`unrecognized configuration parameter "transaction_timeout"`:** The dump came from `pg_dump` 17 or later and the cluster runs Postgres 16. Go back to step 3.
- **`must be owner of extension`:** The dump has a `COMMENT ON EXTENSION` statement for an extension that comes preinstalled on MPG, such as `pgaudit` or `pg_stat_monitor`, and the default user doesn't own those. You'll see this when the source is another MPG cluster. Dump again and leave those extensions out, which needs `pg_dump` 17 or later:
    ```bash
    pg_dump --no-owner --no-acl --exclude-extension=pgaudit --exclude-extension=pg_stat_monitor -f dump.sql "$LEGACY_PG_CONNECTION_STRING"
    ```
- **`server closed the connection unexpectedly`:** The connection to your cluster dropped before the restore finished. A restore needs the connection for the whole run, and a large one can take a while. With `--single-transaction`, nothing was imported, so run the restore again.
- **`already exists`:** An earlier restore without `--single-transaction` left tables, schemas, or types behind. Restore into an empty database instead: create one with `fly mpg databases create <CLUSTER_ID> --name <database-name>`, then add `--database <database-name>` to the restore.
- **Another error you'd rather skip:** Replace `--single-transaction` with `-v ON_ERROR_STOP=0`, as in `fly mpg connect <CLUSTER_ID> -f dump.sql -- -q -v ON_ERROR_STOP=0`. psql then carries on past errors, and the exit status is `0` even when statements fail, so read every error it prints.

### Piping a small database

For a small database you can skip the file and pipe `pg_dump` straight in. Piped SQL keeps psql's defaults, so add the flags that `-f` sets for you. Set `pipefail` as well: without it, a `pg_dump` that fails looks like a restore that worked.

```bash
set -o pipefail
pg_dump --no-owner --no-acl "$LEGACY_PG_CONNECTION_STRING" | fly mpg connect <CLUSTER_ID> -- -X -q -v ON_ERROR_STOP=1 --single-transaction
```

If step 3 applies to you, put the same `sed` command between `pg_dump` and `fly mpg connect`. If the pipe fails, you have to dump again, so prefer the file for anything large.

### Use another tool

Tools that make their own connection, like `pg_restore` with a custom-format dump, need an address to connect to. Run `fly mpg proxy <CLUSTER_ID>` and point the tool at the local port it prints, using the username and password from your cluster's connection string in the dashboard. See [Setting up a Proxy Connection](/postgres/create-and-connect#setting-up-a-proxy-connection).

For larger or more complex databases, you may need to break the dump and restore process into multiple steps. You may also consider using dedicated PG migration tools like [pgloader](https://pgloader.io/) or [pgcopydb](https://github.com/dimitri/pgcopydb).

## Limitations
Some source databases may not be a good fit for importing into a Fly Managed Postgres cluster.  Some common cases that will prevent imports are if your source database:

- Relies on a third party extension that [isn't supported by MPG](/postgres/extensions)
- Is larger than 1 TB (the maximum storage limit for MPG clusters)

Note: While MPG supports up to 1 TB of storage, initial cluster creation is limited to 500 GB. For databases larger than 500 GB, you'll need to create your cluster with the maximum initial size and then expand storage after the import process.

Multi-schema and multi-database imports are supported. If your app uses multiple schemas or databases, imports should work as expected when run with the default `fly-user` or another user with the `schema_admin` role.
