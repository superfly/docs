If you have an existing Django app that you want to move over to Fly, this guide
walks you through the initial deployment process and shows you techniques you
can use to troubleshoot issues you may encounter.

## Configure Django

The official [How to Deploy Django](https://docs.djangoproject.com/en/stable/howto/deployment/) guide and [Django Deployment Checklist](https://docs.djangoproject.com/en/stable/howto/deployment/checklist/) are a good first step to ensure your app is ready for deployment.

The third-party package [WhiteNoise](https://whitenoise.evans.io/en/stable/) is recommended for serving static files in production as this requires [additional configuration](https://docs.djangoproject.com/en/stable/howto/static-files/deployment/).

A production web server must be installed, typically either [Gunicorn](https://gunicorn.org/install/) or [uWSGI](https://uwsgi-docs.readthedocs.io/en/latest/). The database adapter [Psycopg](https://www.psycopg.org/psycopg3/docs/) is commonly used along with [dj-database-url](https://pypi.org/project/dj-database-url/) to establish a Django database connection via a `DATABASE_URL` environment variable.

Be sure to have generated an up-to-date `requirements.txt` file for any new packages added for deployment.

## flyctl

Fly.io has its own command-line utility for managing apps, [flyctl](/flyctl). If not already installed, follow the instructions on the [installation guide](/flyctl/install) and [log in to Fly](/getting-started/sign-up-sign-in).


## Provision Django and Postgres Servers

To configure and launch your Django app with a [Managed Postgres](/postgres) cluster, run `fly launch` with `--db=mpg`:

```bash
fly launch --db=mpg
```

You'll get a summary of the defaults chosen for your app, including a Managed Postgres cluster on the Basic plan, and the launcher asks whether you want to tweak these settings. Type `y` to open the Fly Launch page and change the app name or region, or `n` to accept the defaults.

Once you confirm your settings, the launcher will:

* Create the Managed Postgres cluster, wait for it to be ready, and set the `DATABASE_URL` secret on your app
* Set the `SECRET_KEY` secret
* Generate a `Dockerfile` and `fly.toml` for your Django app

If your organization is on the [Free plan](/about/free-plan), `fly launch --db=mpg` can't create the cluster: launch uses the Basic plan, and the Free plan includes only the \$4 [Developer plan](/postgres/developer-plan). Instead, run `fly launch --no-db --no-deploy`, create a Developer plan cluster with `fly mpg create --plan dev-256`, [attach it](/postgres/create-and-connect) with `fly mpg attach <CLUSTER_ID>`, and then run `fly deploy`.

## Dockerfile and fly.toml

The `fly launch` command creates two new files in the project that are automatically configured: `Dockerfile` and `fly.toml`.

The [Dockerfile](https://docs.docker.com/engine/reference/builder/) is essentially instructions for creating an image.

The [`fly.toml`](/reference/configuration) file is used by Fly.io to configure applications for deployment. Configuration of builds, environment variables, internet-exposed services, disk mounts and release commands go here.

To run Celery workers next to your web process, with Redis as the broker, see [Background job queues](/blueprints/work-queues).

### Complete fly.toml with Celery

Gunicorn, a Celery worker and Celery beat each run in their own [process group](/launch/processes) in `fly.toml`. Here's a full `fly.toml` with Gunicorn serving web traffic, a Celery worker, Celery beat, Managed Postgres and Upstash Redis. Replace `my_app` with your project's module name:

```toml
app = "my-django-app"
primary_region = "ord"

[build]

[deploy]
  release_command = "python manage.py migrate"

[processes]
  app = "gunicorn --bind :8000 --workers 2 my_app.wsgi"
  worker = "celery -A my_app worker -l info"
  beat = "celery -A my_app beat -l info"

[http_service]
  internal_port = 8000
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 0
  processes = ["app"]

[[vm]]
  memory = "1gb"
  cpu_kind = "shared"
  cpus = 1
```

Postgres and Redis aren't `fly.toml` sections. Create them with flyctl, and your app gets their connection strings as the `DATABASE_URL` and `REDIS_URL` secrets:

```bash
fly mpg create --name my-django-db --region ord
fly mpg attach <CLUSTER_ID> --app my-django-app
fly redis create --name my-django-redis --region ord
fly secrets set REDIS_URL="<URL printed by fly redis create>" --app my-django-app
fly deploy
```

- `fly mpg list` shows the cluster ID. See [Managed Postgres](/postgres) for plans.
- Point Celery's broker at `REDIS_URL`, for example `CELERY_BROKER_URL = os.environ["REDIS_URL"]` in `settings.py`.
- Run one `beat` Machine so each scheduled task runs once: `fly scale count beat=1`. Remove the `beat` line if you don't have scheduled tasks.
- Set `internal_port` to the port Gunicorn binds to.

## ALLOWED_HOSTS & CSRF\_TRUSTED_ORIGINS {#allowedhosts-amp-csrf_trustedorigins}
The dedicated URL for your deployment will be `<app_name>.fly.dev`. Update the [ALLOWED_HOSTS](https://docs.djangoproject.com/en/stable/ref/settings/#allowed-hosts) and [CSRF\_TRUSTED\_ORIGINS](https://docs.djangoproject.com/en/stable/ref/settings/#csrf-trusted-origins) configurations with your `<app_name>` to include it.

## Deploy Your Application

To deploy the application use the following command:

```bash
fly deploy
```

This will take a few seconds as it uploads your application, verifies the app configuration, builds the image, and then monitors to ensure it starts successfully. Once complete, visit your app with the following command:

```bash
fly apps open
```

If everything went as planned you will see your Django application homepage.

## Troubleshooting your initial deployment

Since this is an existing Django app, it is highly likely it might not boot because you probably need to configure secrets or other service dependencies. Let's walk through how to troubleshoot these issues so you can get your app running.

### View Log Files

If your application didn't boot on the first deploy, run `fly logs` to see
what's going on.

```bash
fly logs
```

This shows the past few log file entries and tails your production log
files. [Additional flags](/flyctl/cmd/fly_logs) are available for filtering.

### Console

To SSH into your hosted Django application use the command `fly ssh console`. For example, to execute Django's `createsuperuser` command to log into the admin do the following:

```bash
fly ssh console
# python manage.py createsuperuser
```

If you prefer, this can be run as one command instead:

```bash
fly ssh console --pty -C 'python /code/manage.py createsuperuser'
```

<Info>
The `--pty` flag tells the SSH server to run the command in a pseudo-terminal, which `createsuperuser` requires.
</Info>

### Secrets

Secrets allow sensitive values, such as credentials and API keys, to be securely passed to your Django applications. You can set, remove, or list all secrets with the [fly secrets](/apps/secrets) command.

### Git

Deployments are initiated via the `fly deploy` command--git isn't needed to deploy to Fly.io. The advantage of this approach is that your git history will be clean and not full of `git push` commits such as occurs on other hosting platforms.

This also means that `.gitignore` files are not ignored. If you have secrets or other sensitive information in your git history, it is recommended to create a `.dockerignore` file and add the git repo there.

### Databases

[Managed Postgres](/postgres) runs your Postgres cluster for you, with high availability, automatic failover and backups on every plan. If you didn't create a database at launch, create one with `fly mpg create`, find the cluster ID with `fly mpg list`, and attach it with `fly mpg attach <CLUSTER_ID>`. This sets the `DATABASE_URL` secret on your app.

If you still run an older Fly Postgres app, which isn't managed, you [manage it yourself](/unmanaged-postgres), including scaling its Machines when it runs out of disk or memory.

### Custom Domain & SSL Certificates {#custom-domain-amp-ssl-certificates}

After you finish deploying your application to Fly.io and have tested it extensively, [read through the Custom Domain docs](/networking/custom-domain) and point your domain at Fly.

In addition to supporting [`CNAME` DNS records](/networking/custom-domain#cname-records), Fly.io also supports [`A` and `AAAA` records](/networking/custom-domain#a-and-aaaa-records-recommended) for those who want to point `example.com` (without the `www.example.com`) directly at Fly.
